# Shared Jenkins — Configuration as Code

A single Jenkins controller that runs the CI/CD pipelines for several projects from one host.
Everything is declarative: the image and its plugins, the credentials, and every pipeline job are
defined in this repository through **Jenkins Configuration as Code (JCasC)** and **Job DSL**. The
host itself is provisioned with **Terraform**.

The controller runs on a dedicated EC2 instance in `ap-northeast-1` (Tokyo), independent of any
developer machine.

## Pipelines

| Job | Pipeline source | What it does |
|---|---|---|
| `telephony-ec2` | `Telephony-Infrastructure` · `jenkins/Jenkinsfile-ec2` | Standalone EC2 (Docker Compose) deploy. Builds the `freeswitch` branch of `Telephony-Service`. |
| `telephony-missed-call` | `Telephony-Infrastructure` · `jenkins/Jenkinsfile-k8s` | Kubernetes deploy, missed-call campaign. Builds `freeswitch`. |
| `telephony-ivr` | `Telephony-Infrastructure` · `jenkins/Jenkinsfile-k8s` | Kubernetes deploy, multilingual IVR campaign. Builds `freeswitch-ivr`. |
| `agri-catalogue-service` | `Open-Agri-Stack/OAS-Infra` · `jenkins/Jenkinsfile` | Build image → push to ECR → Helm deploy to the private K8s node via bastion ProxyJump. |
| `org-user-notification-services` | `Open-Agri-Stack/OAS-Infra` · `jenkins/Jenkinsfile` | As above. |
| `oas-auth-service` | `Open-Agri-Stack/OAS-Infra` · `jenkins/Jenkinsfile` | As above, plus it configures the Keycloak realm — see [Keycloak realm stage](#keycloak-realm-stage). |

The three telephony jobs are generated by a Job DSL loop; the three OAS jobs are declared
individually. All six are **manual trigger only** — no SCM polling.

Pipeline logic lives in each project's *infrastructure* repository and is loaded via "Pipeline
script from SCM". This repository defines only the jobs and the credentials they consume. The OAS
jobs take **no build parameters**: the `Jenkinsfile` derives the service from the job name and
discovers the bastion, node, and nginx addresses from EC2 tags via `aws-credentials` (which needs
`ec2:DescribeInstances`).

## Repository layout

| Path | Purpose |
|---|---|
| `Dockerfile` | Custom controller image: JDK 17 base plus Maven, Docker CLI, AWS CLI, `kubectl`, `openssh-client`, and `jq`. |
| `casc.yaml` | JCasC — security realm, credentials, and the Job DSL that provisions all jobs. |
| `docker-compose.yml` | Runs the container: host Docker socket mounted, JVM/Maven memory caps, secrets passed through an explicit `environment:` list. |
| `plugins.txt` | Plugins baked into the image at build time. |
| `.env.example` | Every environment variable the stack needs. Copy to `.env` on the host. |
| `terraform/` | EC2 instance, security group, and userdata bootstrap. |

`jq` is required by the OAS auth pipeline's realm stage, which runs a jq-heavy Keycloak Admin API
script on the agent. Removing it breaks that stage.

## Credentials

All credentials are provisioned by JCasC from `.env` — none are created through the UI.

| ID | Type | Consumed by |
|---|---|---|
| `aws-credentials` | AWS key | ECR, and EC2 discovery in the OAS pipeline |
| `github-credentials` | username + token | SCM checkout, all projects |
| `ec2-deploy-key` | SSH key | OAS bastion **and** private K8s node (one shared key) |
| `ES_CREDENTIALS` | username + password | Elasticsearch, both catalogue services |
| `db-password-agri-catalogue` | secret text | Postgres password for `acs_user` |
| `db-password-org-user-notification-services` | secret text | Postgres password for `oas_user` |
| `keycloak-client-secret` | secret text | `oas-auth-service`'s Keycloak client secret |
| `keycloak-admin` | username + password | Keycloak master admin, **realm configuration only** |
| `ssh-private-key` | SSH key | Telephony deploy targets |
| `kubeconfig` | secret file | Telephony Kubernetes deploy |
| `postgres-password` | secret text | Telephony `lead_db` (`lead_user`) |
| `pgadmin-password` | secret text | Telephony pgAdmin login |
| `freeswitch-esl-password` | secret text | FreeSWITCH Event Socket |

The OAS pipeline builds two of these IDs at runtime rather than naming them literally —
`db-password-${SERVICE}`, and the Keycloak IDs from `admin_cred_id` / `client_secret_cred_id` in
`services/<service>.config.yaml`. Searching the `Jenkinsfile` for those literal IDs finds nothing;
they are still required.

## Keycloak realm stage

The `oas-auth-service` pipeline configures the identity provider as part of deploying it. The
`Configure Keycloak Realm` stage runs the application repository's `setup-realm.sh` against the live
Keycloak over an `ssh -L` tunnel through the bastion, so Keycloak itself stays private.

Two prerequisites live on this host rather than in the OAS repository:

- `jq` in the controller image (already in `Dockerfile`).
- `KEYCLOAK_ADMIN_USER` and `KEYCLOAK_ADMIN_PASSWORD` in the host `.env`, which become the
  `keycloak-admin` credential. These must match `KEYCLOAK_ADMIN_USERNAME` / `KEYCLOAK_ADMIN_PASSWORD`
  in the platform's `db-host/.env`.

The stage also compares Keycloak's live client secret against `keycloak-client-secret` and fails the
build if they differ. That is deliberate: a mismatch would otherwise deploy a pod unable to obtain
an admin token, surfacing much later as a failed user publish.

## Operating the controller

**The host directory `~/jenkins` is not a git checkout.** It is a flat set of files copied up, with
`<file>.bak.<timestamp>` kept beside each edit. `git pull` there does nothing — pushing to this
repository does not update the running server.

To apply a change:

```bash
# from a clone of this repo, with the resolved IP in $JENKINS_IP
scp Dockerfile casc.yaml docker-compose.yml plugins.txt ubuntu@$JENKINS_IP:~/jenkins/
ssh ubuntu@$JENKINS_IP 'cd ~/jenkins && docker compose build jenkins && docker compose up -d --force-recreate'
```

`--force-recreate` is required. A plain `docker compose up -d` will **not** recreate the container
when only `.env` changed, so new secrets silently fail to load. Rebuilding is only necessary when
`Dockerfile` or `plugins.txt` changed.

For a `casc.yaml`-only change you can reload in place instead of restarting:

```bash
curl -X POST -u "admin:<password>" "http://$JENKINS_IP:8080/configuration-as-code/reload"
```

> A brand-new `pipelineJob` seeded during a JCasC reload lands on disk but is not registered
> in memory for that boot, so the API returns 404 for it. A second
> `docker compose restart jenkins` picks it up.

### Provisioning the host

```bash
cd terraform
terraform init
terraform plan     # expect no changes against the running instance
terraform apply
```

## Onboarding a project

1. Add a `pipelineJob('<name>')` block to the `jobs:` Job DSL in `casc.yaml`, pointing `cpsScm` at
   the project's repository and its `Jenkinsfile` via `scriptPath`.
2. Declare any new credentials under `credentials.system.domainCredentials`, using `${ENV}`
   placeholders.
3. Add the matching variables to the `environment:` list in `docker-compose.yml` **and** document
   them in `.env.example`. Secrets reach the container only through that explicit list — there is no
   `env_file`, so a variable missing from it leaves its JCasC placeholder unresolved.
4. Set the real values in the host `.env`, copy the changed files up, then recreate the container.
